# BT 运维控制台一期设计

## 背景

当前系统是 Vue/Vite 前端加 Django/DRF 后端，BT 和 SY 两套系统并存。前端已经覆盖设备监控、当前告警、记录查询、帮助、运行参数等功能，但部分网管运维动作仍依赖 Django Admin，例如设备基础数据维护、车间/线路维护、设备导入导出和设备重连动作。

一期目标是新增 BT 运维控制台，让具备权限的用户可以在前端完成 BT 基础运维管理。记录页现有“打开后端界面”入口保留，作为过渡期兜底入口，不在一期移除。

## 范围

一期只做 BT，不做 SY。SY 后续复用同一套页面结构、API 形态和权限策略。

一期包含：

- BT 设备信息的新增、查看、编辑、删除。
- BT 设备的单个和批量重连命令。
- BT 设备的导入预检、导入提交和导出。
- 车间的新增、编辑、启停、排序和备注。
- 线路的新增、编辑、启停、排序和备注。
- 前端新增“运维管理”入口和 `/ops` 页面。
- 后端新增正式 DRF API，不让前端依赖 Django Admin 页面。

一期不包含：

- SY 运维管理。
- 用户和权限管理页面。
- 历史告警、开关量、模拟量、继电器动作、用户操作等历史数据的导出清理增强。
- 清空整表等高风险历史数据管理动作。
- 移除或隐藏记录页的“打开后端界面”入口。

## 用户与权限

用户必须登录才能访问运维控制台。

超级用户可以管理全部车间、线路和设备。

非超级用户按 `user.depots` 限制可管理范围：

- 只能查看和维护自己授权车间内的设备。
- 只能将设备新增或编辑到自己授权的车间。
- 只能对自己授权车间内的设备发送重连命令。
- 只能导出自己授权范围内的设备。
- 导入设备时，如果行数据引用未授权车间，则预检报错，提交拒绝。

运维管理入口建议对 `System Admin` 用户组和超级用户开放。普通用户不可见。后端必须再次校验权限，前端显示控制只作为体验优化。

线路模型当前不绑定车间。一期允许具备运维管理入口权限的用户维护线路；如果后续需要按线路授权，再增加线路授权关系。

## 前端设计

新增 `/ops` 路由和 Header 标签“运维管理”。页面只调用 BT API，例如通过 `getApiBase('bt')` 构造请求。

页面内部采用左侧子导航和右侧工作区：

- 设备信息
- 车间管理
- 线路管理
- 导入导出
- 操作结果

### 设备信息

设备列表支持筛选：

- 车间
- 线路
- 设备 ID
- 设备名称
- IP 地址
- 一方向启用状态
- 二方向启用状态

设备列表展示：

- 设备 ID
- 设备名称
- 车间
- 线路
- IP 地址
- X/Y 坐标
- 一方向邻站 ID
- 一方向邻站方向
- 二方向邻站 ID
- 二方向邻站方向
- 一方向启用
- 二方向启用
- 过滤告警码
- 备注

行操作：

- 编辑
- 复制新增
- 删除
- 发送重连命令

批量操作：

- 批量删除
- 批量导出
- 批量发送重连命令

删除、批量删除、单个重连和批量重连都需要二次确认。

设备删除按现有模型关系执行硬删除，可能级联删除该设备关联的采集记录、告警记录、继电器动作和用户操作记录。前端确认文案必须明确提示级联影响；后端只允许删除用户授权车间内的设备，并在操作结果中返回删除成功和失败明细。

设备表单字段来自现有 `Device` 模型。车间和线路使用 API 下拉选择。邻站用设备搜索选择，最终提交邻站设备 ID，避免手填错误。

### 车间管理

车间支持：

- 新增
- 编辑名称
- 启停
- 排序
- 编辑备注

车间被设备引用时不做硬删除。一期通过启停表达停用，避免破坏设备关系。

非超级用户只能看到和维护自己授权的车间。

### 线路管理

线路支持：

- 新增
- 编辑名称
- 启停
- 排序
- 编辑备注

线路被设备引用时不做硬删除。一期通过启停表达停用，避免破坏设备关系。

## 后端设计

新增 BT 运维 API，建议路径如下：

```text
GET/POST          /api/ops/depots/
GET/PATCH         /api/ops/depots/{id}/
GET/POST          /api/ops/lines/
GET/PATCH         /api/ops/lines/{id}/
GET/POST          /api/ops/devices/
GET/PATCH/DELETE  /api/ops/devices/{id}/
POST              /api/ops/devices/bulk-delete/
POST              /api/ops/devices/reconnect/
GET               /api/ops/devices/export/
POST              /api/ops/devices/import/preview/
POST              /api/ops/devices/import/commit/
```

后端不复用 Django Admin 页面。Admin 中已有的导入导出、重连命令和权限过滤逻辑应抽到可复用服务函数，供 Admin 和 API 共用。

推荐拆分服务：

- `ops_permissions`：用户入口权限、车间范围过滤、设备范围过滤。
- `device_import_export`：设备导入预检、导入提交、导出。
- `device_commands`：设备重连命令发送。
- `ops_audit`：用户操作日志记录。

所有写操作必须由后端校验权限。服务端拒绝未授权车间、未授权设备、重复设备 ID、重复 IP、无效邻站和无效线路。

## 导入导出

设备导出遵守当前筛选和车间权限。导出字段与 Admin 设备导出保持一致：

- 设备 ID
- 设备名称
- 车间
- 线路
- IP 地址
- X/Y 坐标
- 一/二方向邻站 ID
- 一/二方向邻站方向
- 一/二方向启用
- 备注
- 过滤告警码

导入采用两步：

1. `import/preview` 只解析和校验，不写数据库。
2. `import/commit` 使用预检后的数据写入数据库。

预检需要返回新增数量、更新数量、错误数量和逐行错误。阻塞错误存在时不允许提交。

导入校验规则：

- 设备 ID 必须存在且唯一。
- IP 地址必须存在且唯一。
- 车间名称必须存在，且用户有权限。
- 线路名称必须存在。
- 邻站 ID 必须存在或为空。
- 方向启用字段必须能解析为布尔值。
- 告警过滤码必须能解析为整数数组。

## 重连命令

重连命令复用后端已有 Redis Stream 发送逻辑。API 接收设备 ID 列表，后端逐台校验设备权限并发送命令。

返回值包含：

- 总数
- 成功数量
- 失败数量
- 跳过数量
- 每台设备的结果和失败原因

成功发送后写入 `UserOperation`。单台或批量重连均记录操作人。

## 错误处理

API 使用统一错误结构：

```json
{
  "detail": "导入失败",
  "errors": [
    {"row": 5, "field": "ip_address", "message": "IP地址已存在"},
    {"row": 8, "field": "depot", "message": "无权管理该车间"}
  ]
}
```

前端在表单字段旁显示字段错误，在导入预检表格中按行展示错误，在批量操作结果中展示成功、失败和跳过明细。

## 测试策略

后端接口测试覆盖：

- 超级用户可以查看和维护全部数据。
- `System Admin` 用户只能查看和维护授权车间内的数据。
- 普通用户不能访问运维 API。
- 未授权车间写入被拒绝。
- 设备新增、编辑、删除成功路径。
- 设备 ID 和 IP 唯一性校验。
- 导入预检新增、更新和错误统计。
- 导入提交不会写入未授权车间数据。
- 批量删除只删除授权范围内设备。
- 重连命令只发送到授权范围内设备，并返回逐台结果。

前端验证覆盖：

- `vue-tsc --build --force`
- `vite build`
- 手工验证超级用户、系统管理员和普通用户的入口可见性。
- 手工验证导入错误能定位到行和字段。
- 手工验证重连成功、失败和操作日志。
